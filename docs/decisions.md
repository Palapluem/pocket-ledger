## D-03 Money, balance signs and account compatibility

Agreed for Sprint 1 by Wisit on 15 November: THB only, integer satang, a maximum amount, non-negative opening balances and no overdraft or overpayment.

Normal balances: Cash is money held; Loan Given is money receivable; Loan Taken is debt owed; Income and Expense record their respective classifications. The effect table in the System SDS makes each sign explicit, including the `PAYMENT` form used both for a payment from Cash and a charge to Loan Taken. All referenced financial accounts must belong to the acting User. An Administrator never gains financial access. The two required transaction forms and their assignment-defined allocation categories must remain supported by the product baseline.

The required property is atomicity: a rejected or failed transaction leaves no partial transaction, allocation or balance effect. The team agreed the following Sprint 1 rules in PR #15:

- Amounts: THB only; a transaction or allocation amount is a decimal string greater than 0 with at most two decimal places, parsed exactly into integer satang (no rounding; more decimals are rejected). Maximum single amount 1,000,000,000.00 THB; store satang as `bigint`.
- Forms: `PAYMENT` has a Cash primary account (payment) or a Loan Taken primary account (charge, for example a credit-card purchase); `RECEIVE` has a Cash primary account. Any other primary type is rejected.
- Allocation: at least one allocation line; the allocation sum must equal the transaction total exactly. Every referenced account belongs to the acting User, and each allocation account type must be allowed for that form by the System SDS effect table. No line may reference the primary account, and an account may appear in at most one line of a transaction. Mixed lines of different allowed types are allowed.
- No negative balances: a transaction is rejected (422) if it would make a Cash account balance below zero, or reduce a Loan Taken (debt) or Loan Given (receivable) balance below zero (no overpayment). The check runs inside the same database transaction as the write, against locked current balances.
- Atomic rejection: any validation, ownership or balance failure writes nothing; a persistence failure rolls back the whole request. The draft Sprint 1 journey uses only the documented salary, split card purchase and bank-to-card repayment cases.

## D-04 Dates, opening balances and correction boundary

Agreed by Wisit on 15 November: dates are calendar dates in YYYY-MM-DD form, interpreted in Asia/Bangkok, with inclusive from/to ranges for history and summaries. An opening balance is at least 0 and has an opening date. A transaction date must be on or after the opening date of its primary account and every referenced balance-bearing account (Cash, Loan Taken or Loan Given), and not later than today in Asia/Bangkok. Income and Expense are classification accounts and do not impose an opening-date cutoff. Opening balance/date may be changed after activity exists only if no resulting balance is negative and no existing transaction is before the revised opening date of an affected balance account. Such a change recalculates derived history; Sprint 1 does not create a separate audit event for the opening-balance edit.

On 16 November 2026, Wisit confirmed while resolving PR #25's review that an opening date later than today's Asia/Bangkok calendar date is invalid. The API rejects it with `422 RULE_VIOLATION`, and the date input caps the selectable date at today. N0TAW00D re-reviewed and approved the updated PR head; PR #25 merged into `sprint-1-staging` at `53c20ff`.

Agreed by Wisit on 15 November: Sprint 1 creates transactions without a server idempotency key; the UI disables repeat submission while a request is in flight, and clients must not automatically retry a transaction POST. If a response times out after a possible commit, the user checks history before manually retrying. A repeated POST can create a duplicate; Sprint 1 does not promise exactly-once delivery. Sprint 2 adds transaction correction by edit with derived balances recalculated (its contract is written then). Sprint 3 adds the editable duplicate feature. This deferral does not remove correction or duplication from the product baseline.

## D-05 Authentication and deactivation

Agreed Sprint 1 model: first-party stateless signed JWT in an HttpOnly cookie for seeded-user sign-in. The JWT carries the user identifier, display name and role snapshot plus standard issuer, audience, issue-time and expiry claims. Approved by Wisit: a 3600-second lifetime, HS256 as the fixed algorithm and the `jose` library. The current implementation reads its key from `JWT_SECRET` (at least 32 bytes). Agreed by Wisit on 15 November: keep a cryptographically random key of at least 32 bytes in an ignored local `.env` or deployment secret store, never in Git; rotate it manually by replacing the secret and restarting; invalidate all outstanding tokens on rotation; and retain no previous key. The Origin/CSRF request-protection policy is deferred for now, as Wisit requested; the current Origin check is optional implementation hardening, not an agreed team policy or a blocker to this PR. Revisit and agree the production protection before public deployment.

This simple design has no server-side session row, refresh token or revocation list. Logout clears the current browser cookie; a copied token remains valid until expiry. A role change or account disable does not affect an existing token before expiry while its signing key remains accepted; new sign-ins use the current user record. Do not claim immediate revocation or current-account checks on every request. Both students accept these token limitations. The lifetime, algorithm, library and key-management policy above are agreed. Request protection remains deferred until deployment review; do not treat the current Origin check as a settled policy. Change the design if immediate revocation becomes necessary.

Use an adaptive one-way password hash from a trusted library, never reversible password encryption. Protect the JWT in an HttpOnly, SameSite=Lax cookie and enable Secure under HTTPS. Validate signature, fixed algorithm, issuer, audience and expiry. The team deferred a formal Origin/CSRF policy; choose and verify the production request-protection policy before public deployment. Seeded identities are sufficient. Public signup, email delivery and password recovery are outside Sprint 1. This is the team's selected design, not a course requirement or an implementation result.
