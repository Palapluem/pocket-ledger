## Independent fixture and expected values

Use User A and User B with distinct seeded financial accounts and one Administrator with no financial accounts. Keep synthetic credentials private or generated by safe local seed. Each enabled User receives five distinct accounts: Bank (Cash), Credit card (Loan Taken), Salary (Income), Dining and Groceries (Expense); Sprint 1 does not seed Loan Given. Seeded accounts use the Bangkok seed date; the transaction API fixture independently sets the Bank and Credit card opening date to 2026-11-01. Seed reruns preserve existing account/opening/transaction values. The card purchase is a `PAYMENT` with the card as primary account; repayment is a `PAYMENT` from the bank allocated to the card.

| Action | Bank / card debt | Income / Expense |
| --- | --- | --- |
| 2026-11-01: set opening bank balance 10,000; card opening zero | 10,000 / 0 | 0 / 0 |
| 2026-11-02: receive salary 20,000 into bank | 30,000 / 0 | 20,000 / 0 |
| 2026-11-03: charge 1,200 to card: dining 700 + groceries 500 | 30,000 / 1,200 | 20,000 / 1,200 |
| 2026-11-04: repay card 500 from bank | 29,500 / 700 | 20,000 / 1,200 |

These expected values are written independently. Do not call the production balance helper to compute the expected side of an assertion. Invalid allocation 700 + 400 against total 1,200 must leave the entire pre-request state unchanged. D-03 and D-04 record the agreed date, amount-limit, overpayment and insufficient-funds policies. Payment-side boundaries and atomicity are covered by Issue #21; F-03/F-04 opening-state and receive-side cases are covered by Issue #20 at `0b478aa`. Sprint 1 has no server idempotency key: a transaction POST is not automatically retried; an ambiguous timeout requires checking history before a manual retry, and duplicate creation remains a documented limitation.
